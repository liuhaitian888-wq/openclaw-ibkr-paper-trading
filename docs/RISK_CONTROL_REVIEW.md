# 风控分类与成熟项目方法核对

核验日2026-11-09。不存在统一的“必须有N种风控”；应按账户、资产、订单路径和故障方式覆盖。下面是本项目工程分类，不是法规条文的固定分类，也不是已经取得合规认证。

## 需要覆盖哪些风险

|类别|控制目标与建议处理|本项目事实/缺口|
|---|---|---|
|身份与权限|Paper/Live/账户/合约精确绑定，来源分层，唯一执行owner；持续保留|已有manifest、锁、scope；未授权不能因网络恢复放行|
|数据与时段|真实时间戳、新鲜度、PIT/复权、交易日、停牌、订阅权；失效阻止新增风险|已修quote时间戳；新时段提醒不代替execution guard；实时数据/停牌验收仍未闭环|
|订单正确性|tick/精度、数量、价格偏离、重复ID、频率、部分成交/撤改并发|候选硬限制与持久UNKNOWN已有；连续executor联合验收仍P0|
|资金与FX|可用/已结算现金、费用预留、实时汇率方向/新鲜度、无新增借款|Paper一次现金换汇已原生对账；连续执行资金与currency canonical待收口|
|组合风险|总/净敞口、单名/行业集中、相关性、外部单与旧仓均计入|五项附加限额可空，已有硬兜底；不能因无本地intent忽略外部订单|
|交易中保护|原生联动、覆盖数量、reduce-only意图、gap/滑点、移动保护的撤改窗口|PFE旧保护保留；五只旧仓有限补保护等待真实时段，不宣称已装好|
|运行韧性|连接/认证、重启对账、进程唯一、资源生命周期、备份恢复、告警|已有共享依赖/恢复注册表；网络恢复不等于业务许可|
|模型与研究|过拟合、幸存者、泄漏、费用、OOS、极端情景与容量|已有只读覆盖实验与证据；完整PIT多标的长期回测缺口需秘书主动提出|
|执行质量|价差、深度、冲击、成交率、拒单与成本；依流动性决定订单分拆|不是把QMAX固定1股；批量/多标的需逐笔原子预算与组合预留|
|合规与审计|账户规则、产品/做空资格、市场滥用、行情授权、账本可追溯|持久事件、权限来源与记录已存在；适用法需按司法辖区、客户身份及业务模式确认|

止损不是收益/最大损失保证：跳空、停牌、流动性不足、券商拒单和系统失联都可能使实际退出偏离触发价。成熟运行后可以调整策略限额，不能因此移除身份、资金、幂等、对账和故障停止保障。

## 别人的方法：借鉴到什么程度

- [QuantConnect/LEAN Risk Models](https://www.quantconnect.com/docs/v2/writing-algorithms/algorithm-framework/risk-management/supported-models)：研究单标的/组合回撤、行业集中、移动止损等可组合模型。其风险目标调整不自动证明IB原生保护闭环。本次作为研究/分类参考，未引入这些模型，也不声称已回测有效。
- [NautilusTrader稳定版执行架构](https://nautilustrader.io/docs/latest/concepts/execution/)：参考风险检查与执行/对账分层。其当前文档包含价格数量校验、notional、状态与节流；需要验证全部提交/修改/模拟释放路径，不能只看一个入口。本次未安装该引擎或复制代码。
- [exchange_calendars](https://github.com/gerrymanoim/exchange_calendars)：参考session、下一session和交易所时区处理；本次采用核验官方年表的轻量实现，未声称库已接入。Milan ETFplus竞价与通用XMIL不能混用。
- [IBKR TWS API官方文档](https://www.interactivebrokers.com/campus/ibkr-api-page/twsapi-doc/)及本项目既有ib_async适配：券商回调/订单状态是原生结果证据，API调用成功不等于交易闭环。当前依赖既有适配，未因研究其他项目更换生产网关。

以上是本轮查阅与借鉴记录，不是全项目历次第三方依赖清单；完整依赖/许可证清单应从锁文件与源码来源单独生成。旧项目审阅副本保留，不按年龄删除。

## 合规边界

[欧盟RTS6 / 2017/589](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:32017R0589)对适用的算法交易投资企业规定测试、变更治理、阈值、实时监控和紧急功能等。它是工程参考，不能据此推定私人自营零售账户全部承担投资企业义务，也不能宣布本项目已合规。

[SEC Rule15c3-5](https://www.sec.gov/rules-regulations/2011/06/risk-management-controls-brokers-or-dealers-market-access)约束具有市场接入的broker/dealer，包含信用/资本及错误订单防控和受控访问。不是要求本个人系统复制券商全部控制；本系统不能绕过适用的券商规则。后续应明确账户服务实体、税务居住地、是否代客/收费/提供建议、资产和数据许可，再核对实际义务。

## 哪些控制不应机械叠加

策略股数上限与金额上限可以按需求选择；相同风险不要散落多份不一致数值。附加字段为空代表不加该层阈值，不代表取消账户/资金/执行安全。风险降低的平仓与补保护不能盲目套新增风险逻辑；但必须证明实际减仓、数量不超持仓、不误撤外部单。通知可按类别关闭，关键故障和UNKNOWN仍需可见。不要把盘前、开盘竞价、常规时段重复当作三套金融授权。

## 后续讨论，不在本次放宽

- 极端大涨大跌时多标的批量/分拆、容量、组合预留和大规模预算。
- 用压力测试、最大容许损失、流动性/滑点和覆盖率决定逐步提高限额的量化标准。
- 固定/ATR/估值触发/移动止损的冲突和gap处理；由秘书用可复查数据研究，再经执行闭环验证。
- 是否取消某些策略附加限制由证据决定；不把保护单当作无限风险授权。

实际清理原则：字段可空不应等同于绕过底层安全；同一门禁在UI、持久配置与执行硬上限之间必须有明确生效优先级。未来检查还需按副作用范围区分未知通知与未知券商订单，既不重放未知通知，也不把无关实体的故障误当成所有交易的同一发生事件。此项是待独立核实问题，不在本次通知部署中默改执行许可。
