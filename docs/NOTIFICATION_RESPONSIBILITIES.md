## 谁接收什么

| 内容或发送类型 | 目标 | 内容要求 |
|---|---|---|
| 公开市场资讯、公司财报解读、研究报告、开闭市/休市提醒 | deehub | 解释主要观点、来源、数据日期及缺口；不夹带本人账户信息 |

| 普通服务故障/恢复、数据更新、日报生成/投递状态 | deehub | 简短状态、时间及事件编号；凭据、个人数据、详细安全诊断留私聊 |
| 已对账允许补发的公开报告 | deehub | 同条补发内容附原因、原定时间、原事件编号；保存新的发送尝试及回执 |
| 即时聊天、追问、确认和秘书对用户的直接答复 | 本人秘书私聊 | 原生身份和private类型核验，群消息不触发执行 |
| 立即影响项目的风控/门禁/操作决策、安全、认证及本人账户信息 | 本人秘书私聊 | 优先于自动消息分类；模型解释不能扩大执行权限 |

| HealthchecksBot故障/恢复 | 既有独立通道 | 不冒充秘书，不把外部机器人发信算成本机器人已有回执 |

同一任务同时含公开和私人内容时，设计上拆成不含私人数据的群摘要和私聊详情。折叠、剧透、主题、标签或静音不是普通群消息的逐成员阅读权限。不得先公开敏感原文再靠删除弥补。owner已明确选择完整账户日报发群，所有成员均可见；该选择不因成员标签改变。

## 数据库留痕和秘书恢复判断

当前本机器人投递使用`notification_outbox`记录内容/事件和状态，`notification_delivery`记录尝试/ACK时间，`notification_receipts`保存chat_id、message_ids与Telegram服务端时间。`TELEGRAM_ACCEPTED`表示服务器确认，不是手机弹窗或已读。`UNKNOWN`表示已进入可能发送阶段但没能确认最终结果，可能是回执丢失、传输异常、进程或存储故障；单凭此状态不能断言云掉线。11月9日1094仍无回执，旧journal只记UNKNOWN，没有保存异常原因。主机uptime起点为10月23日，未显示该时刻整机重启；这不能排除短时断网。

目标恢复流程（尚未实施完整自动闭环）：

1. 本机器人每次原始发送、编辑、补发都要保留事件身份、内容/附件指纹、分类、收件人、发送尝试、异常类型、回执、秘书判断依据和最终状态；多次尝试必须追加，不覆盖原记录。敏感详情留私有库，模型只取必要证据。外部机器人及手工群消息单独标来源，缺少原生回执时保留未核验。
2. 依赖恢复或发现未闭环记录后，现有唯一owner触发一次有界核对；秘书读取上述数据库及可信恢复证据，给出ALREADY_ACCEPTED、PROVEN_UNSENT或UNRESOLVED判断和依据，保存判断。模型不能自行将UNKNOWN改成未发送。
3. 已有原生接收证据：修复本地归档/状态，不补发。明确未发送/Telegram明确拒绝且根因解除：允许现有发送owner立即创建关联补发尝试，受持久锁、到期/新鲜度、目标身份和次数预算约束。旧文件指纹不符不能冒充原报告。
4. 仍不确定是否已被接收：保存UNKNOWN及原因，秘书私聊简短说明；只有完成对账或owner明确接受可能重复的这一次发送后才另行处理。恢复联网本身不是安全重发证明。
5. 获准公开补发时，在同条报告写“补发｜原定…；原因…；关联事件#…”；原因未查明就如实写未查明。结果私聊简报也独立落库，不因通知失败形成无限通知循环。重发不执行交易，不启动第二个发送进程。

当前秘书已有受限只读SQL工具，能查询登记数据库；“网络恢复后自动调查→模型判断→受控补发→双路回执”尚未接通，不能把SQL能力或计划当成已运行。即使模型暂不可用，原发送状态仍可靠保存、确定未发送的既有重试按原边界运行，UNKNOWN不会被清空。

## 成员标签和权限模型

建议成员记录以`(chat_id, telegram_user_id)`为主键，保留标签、批准者、批准时间、版本、可看数据类别和撤销状态。展示标签与真实能力分别保存。建议角色：本人、研究协作者、访客、系统机器人；新成员默认为未分类/访客，不因群管理身份、姓名或自行设置标签取得账户查询/控制权限。具体成员标签尚未分配，也未新增权限。

公开消息仍对群成员可见。需要给部分成员长期共享资料时，方案是独立私有群/频道或按身份核验后私聊投递；不能把同一普通群消息依靠本地标签藏起来。群内临时定向消息可作为查阅提示的研究候选，因离线不保证送达而不承担日报/安全提醒的唯一交付。
