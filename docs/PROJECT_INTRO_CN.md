# 买 der：没有股票基础，也能看懂的项目简介

维护日期：2026-11-10。读完后，你应该能说清这个项目做什么、交易想法怎样变成订单，以及为什么“系统正常”不等于“可以交易”。

## 30 秒认识它

股票可以理解为一家公司的小份额所有权，价格会变化。买 der 研究的是：能否把观察股票、筛选机会、控制风险和记录结果变成一套有规则、能检查的流程。

你可以把它想成一个有记录本的研究助理：帮你收集信息，按规则提出想法，交给风险检查，再记录后续发生了什么。它使用 IBKR（盈透证券）的模拟交易环境做验证。项目目标包括自动化，但当前持续自主下单尚未启用。

它首先要回答“依据是什么、是否允许、结果能否核对”，收益表现需要另外拿证据检验。

## 项目大纲：先解决行情额度有限的问题

> 当行情额度有限时，怎样从大量股票中找到机会，同时把实时行情留给最需要盯住的股票。

这是六层股票池的核心设计问题。实时行情就像数量有限的监控屏幕：总名单可以很大，每只股票却不必始终占用一个屏幕。先用基础资料、低频数据和扫描器缩小范围，再把持续订阅优先留给已有持仓、活动订单和接近信号的股票，其余候选轮换观察。轮换存在等待时间，不能承诺全市场秒级无遗漏。

阅读大纲：

1. **为什么需要六层**：行情权限、并发线路与请求速率是不同限制；六层负责缩小关注范围，订阅调度器负责分配额度。
2. **从哪里开始**：总名单关联本人登记的行情套餐；缺少实时行情仍可关注，显示未登记、非实时或待核验。
3. **怎样进入候选**：合格、扫描、观察、信号就绪分别有条件；秘书可以只读查看已保存名单与时间。
4. **谁应该一直被盯住**：持仓／活动订单优先，热点候选次之；监测覆盖不足需要明示。
5. **怎样知道行情真的可用**：订阅声明、Paper共享、实际报价类型、新鲜度和会话故障分别记录。
6. **怎样持续核查**：秘书抽查已有证据，权限被拒绝时提示核对套餐；会话初始化与账户回读通知分开。

本项目六个canonical名称和迁移规则是当前仓库的实现。本次查到LEAN有相近的Universe Selection与订阅管理机制，但没有找到与这六层完全同名同规则的上游设计；不宣称这个通用思路首次由本项目提出。上游来源、秘书命令及交付边界见[行情订阅与会话说明](MARKET_SUBSCRIPTIONS_AND_SESSION.md)。

## 项目大纲：消息、成员权限与恢复

- **deehub承载非敏感自动发布**：市场资讯、研究报告、任务进度/结果、工程周报、普通运维状态及获准补发的简短说明。
- **秘书私聊承载本人交互与敏感事项**：即时聊天和答复、本人账户、安全/认证、立即影响项目的风控门禁与操作确认。混合任务拆成公开概述和私人详情。
- **每次投递都能核对**：本机器人按事件、内容和收件人保存排队、尝试、失败/未知、原生接收回执与补发关系；已接收不等于手机弹窗。其他机器人/人工消息另标来源，不伪造本机器人回执。
- **断线恢复后先判断再补发**：秘书查库解释，已接收的不重复发；确定未发送且依赖恢复的由既有owner补发，群内同条报告附原因和原定时间；仍不确定的保留UNKNOWN并私聊说明。
- **成员标签和阅读权限分开**：按稳定用户ID登记角色/能力，不按名字或展示标签授权；普通群消息不能靠标签对部分成员隐藏。Telegram支持机器人定向临时消息，但离线送达不保证，不能代替持久日报。

以上是2026-11-10更新的职责和恢复设计。成员标签/细粒度权限、自动对账补发尚未实施；含本人账户信息的日报收件方案仍待选择，不能据此称现有账户日报已脱敏。完整分类、现状与剩余项见[通知职责纲要](NOTIFICATION_RESPONSIBILITIES.md)，上游证据见[Telegram权限调查](TELEGRAM_ACCESS_RESEARCH_20261110.md)。

## 先认识 8 个词

| 词 | 白话解释 |
| --- | --- |
| 行情 | 某个时间看到的价格等市场信息；旧价格可能不适合现在决策 |
| 股票池 | 按条件整理的一组股票名单，入选不等于要买 |
| 策略 | 一套事先写好的观察、买卖和退出规则 |
| 信号 | 策略发现条件满足后提出的候选行动，仍需检查 |
| 风控 | 检查资金、已有持仓、数据和操作权限等，决定是否拦住行动 |
| 订单 / 成交 | 订单是发给券商的买卖请求；成交是请求实际执行，二者有区别 |
| 持仓 | 账户目前持有的股票及数量 |
| 对账 | 把本地记录与券商回报核对，确认实际发生了什么 |

## 跟着一笔假想交易走一遍

下面的甲公司、价格和规则都是教学假设，不是实际推荐，也不是当前生产参数。

假设甲公司股价为 100 元。某条规则观察最近几天的平均价格，发现近期价格走强，于是提出“考虑买 1 股”。这只是信号。价格走强也可能很快反转。

```text
看到行情 → 从股票名单筛选 → 规则产生信号 → 风控与权限检查
                                             ↓
                                  未通过：记录原因，停止
                                  通过：仅在批准范围内提交订单
                                             ↓
                                  等待券商回报 → 对账 → 写入报告
```

风险检查可能发现行情已经过期、资金不足、已有太多同类持仓，或者系统仍在暂停。任何一种情况都可能让流程停下。即使候选股票“很好”，也不能跳过检查。

如果获准发送一张“最多出 100 元买 1 股”的限价订单，市场没有合适卖方时，它可能一直不成交。只有券商确认成交，才可据此更新成交记录；结果不明确时先核对，不能再发一单碰碰运气。

假设后来以 103 元卖出，买入与卖出之间的价差是 3 元，实际净收益还要考虑费用等因素。若仍未卖出，按当前价格估算的盈亏会继续变化。示例里的“元”只用于讲算术，真实报表必须区分币种。

## 项目里的六项工作，各自负责什么？

| 工作 | 对应问题 | 你能看懂的产物 |
| --- | --- | --- |
| 数据 | 现在看到了什么？信息有多新？ | 带时间的价格、账户和订单信息 |
| 研究 | 这个想法有证据吗？ | 假设、验证方法和待解决问题 |
| 策略 | 什么条件下提出行动？ | 信号及触发原因 |
| 风控 | 这次行动是否允许？ | 通过或拦截原因 |
| 执行 | 券商是否收到、是否成交？ | 订单状态、成交回报 |
| 审计 | 能否还原整件事？ | 事件记录、对账和报告 |

这六项是职责划分，不代表每项都已完成生产验收。AI 可以辅助分析与解释；持续自动研究、复盘和策略改进的完整闭环仍需验证，分析本身不能修改交易权限。

## 为什么股票要分成六层？

六层逐步缩小观察范围，使有限的实时行情额度优先覆盖关键股票。这里的六层是股票状态，与上一节六项工作不是同一件事。

| 层 | 白话理解 | 代码中的名称 |
| --- | --- | --- |
| 1 | 登记在总名单里 | `MASTER_UNIVERSE` |
| 2 | 符合基础筛选条件 | `ELIGIBLE_UNIVERSE` |
| 3 | 正在扫描 | `SCAN_POOL` |
| 4 | 值得重点观察 | `WATCH_POOL` |
| 5 | 形成可进一步检查的信号候选 | `SIGNAL_EXECUTION_READY_POOL` |
| 6 | 进入模拟执行或持仓管理状态，具体看订单和成交证据 | `PAPER_EXECUTION_POSITION_POOL` |

进入第 5 层仍不等于允许下单，第 6 层也不能单凭层名认定已成交。报表里另有七池视图，它是不同的展示分类；详细映射见[总体设计与状态](SYSTEM_STATUS_20261106.md)。

## 怎样查看真正的总名单？

秘书的 `/universe` 现在读取按官方目录维护的ABC范围上市证券，而不是只读运行中的少量候选。可用 `/universe network=C type=STOCK` 筛NASDAQ普通股份，用 `/universe permission=PENDING` 看实时权限待核验的条目。ETF和其他证券单独标记，/eligible仍只看实际合格候选。原先只有3条的根因及LEAN做法见[总名单维护说明](ABC_SECURITY_MASTER.md)。

## 怎样读一份报告？

先看时间与环境：这是模拟账户还是其他环境？数据是什么时候采集的？接着看账户与持仓，再看信号、拦截原因、订单和成交。最后看盈亏的计算范围及对账是否完成。

| 看到的词 | 应怎样理解 |
| --- | --- |
| 信号 BUY | 规则提出买入候选，还不能据此认定已经买入 |
| 订单已接受 | 券商接受了请求，之后仍可能未成交或被取消 |
| UNKNOWN | 证据不足，需要核对；不能自行当作失败再发一次 |
| Up / 恢复 | 对应监测检查恢复；行情、业务门禁要分别看 |
| 盈利 | 先确认是否卖出、是否扣费、币种和统计期间 |

回测是用历史数据演练；模拟交易是在模拟环境里观察订单流程；真实资金交易会承担实际损失。前两者的结果都不能保证第三者表现。这个项目目前也没有已验证的稳定盈利结论。

## 不用安装，先确认自己看懂了

1. 规则提示 BUY，但系统 PAUSED，要不要下单？**不要，信号不能越过暂停门禁。**
2. 订单显示已接受，可以说买到了吗？**还不行，要看成交回报。**
3. 通知显示 Up，就可以自动交易吗？**不能，连接与交易许可分别判断。**
4. 一次模拟赚了钱，能证明策略长期有效吗？**不能，还要检查样本、成本、风险和不同市场表现。**

能解释这四题，就已经掌握阅读本项目的基本方法。下一步可看[详细系统状态](SYSTEM_STATUS_20261106.md)；需要理解实现时，再读[中文工程交接手册](PROJECT_HANDOFF_MANUAL_CN.md)。
